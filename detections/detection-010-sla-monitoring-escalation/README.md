# Detection 010 - Automated SLA Monitoring and Escalation

## Overview

Detection 010 adds automated Service Level Agreement (SLA) monitoring and escalation to the Automated SOC Detection & Response Lab.

SOC cases are often assigned response or investigation deadlines based on incident priority. A case that is initially within SLA can become operationally urgent as its deadline approaches or is exceeded.

This detection introduces an SLA monitoring engine that evaluates:

- Case priority

- Case creation time

- SLA due time

- Current evaluation time

- Remaining SLA time

- SLA state

- Required escalation level

The engine dynamically classifies cases as:

```text

WITHIN_SLA

AT_RISK

BREACHED

```

and determines whether escalation is required.

## SLA Status Logic

The monitoring engine calculates:

```text

Case Age = Evaluation Time - Created Time

Remaining SLA = Due Time - Evaluation Time

```

The resulting SLA state is determined using the following thresholds.

| Condition | SLA Status |

|---|---|

| More than 60 minutes remaining | WITHIN_SLA |

| 0 to 60 minutes remaining | AT_RISK |

| Deadline exceeded | BREACHED |

A negative `remaining_minutes` value indicates that the SLA deadline has already passed.

---

## Escalation Logic

SLA status and case priority determine the escalation action.

| SLA Status | Priority | Escalation |

|---|---|---|

| WITHIN_SLA | Any | No Escalation |

| AT_RISK | P3/P4 | SOC Lead Warning |

| AT_RISK | P1/P2 | Immediate SOC Lead Escalation |

| BREACHED | Any | Management Escalation |

This allows high-priority cases to receive stronger escalation before the SLA is breached.

---

## Deterministic Evaluation

The engine supports a controlled evaluation timestamp using:

```text

--evaluation-time

```

This makes the lab tests deterministic.

Instead of depending on the current system clock, the same SOC case can be evaluated at different points in its lifecycle.

Example:

```text

Case Created

03:56 UTC

   |

   +-- 05:56 UTC --> WITHIN_SLA

   |

   +-- 11:26 UTC --> AT_RISK

   |

   +-- 12:26 UTC --> BREACHED

```

If `--evaluation-time` is not provided, the engine uses the current UTC time.

## Test Scenarios

Four scenarios were used to validate the SLA monitoring logic.

| Scenario | Priority | Case Age | Remaining | SLA Status | Escalation |

|---|---|---:|---:|---|---|

| Normal Case | P3 | 120 min | 360 min | WITHIN_SLA | No Escalation |

| Approaching Deadline | P3 | 450 min | 30 min | AT_RISK | SOC Lead Warning |

| High-Priority Approaching Deadline | P2 | 450 min | 30 min | AT_RISK | Immediate SOC Lead Escalation |

| Deadline Exceeded | P3 | 510 min | -30 min | BREACHED | Management Escalation |

---

## Scenario 1 - Case Within SLA

The baseline P3 case is evaluated at:

```text

2026-08-14T05:56:12.686158+00:00

```

At this point:

```text

Case Age:          120 minutes

Remaining SLA:     360 minutes

Priority:          P3

```

### Result

```text

SLA Status:          WITHIN_SLA

Escalation Required: False

Escalation Level:    No Escalation

```

The case has sufficient investigation time remaining and does not require escalation.

---

## Scenario 2 - Case Approaching SLA Deadline

The same P3 case is evaluated at:

```text

2026-08-14T11:26:12.686158+00:00

```

Only 30 minutes remain before the SLA deadline.

```text

Case Age:          450 minutes

Remaining SLA:      30 minutes

Priority:          P3

```

### Result

```text

SLA Status:          AT_RISK

Escalation Required: True

Escalation Level:    SOC Lead Warning

```

The case is still within its SLA but requires attention because the deadline is approaching.

---

## Scenario 3 - High-Priority Case Approaching Deadline

A P2 version of the same SOC case is evaluated with 30 minutes remaining.

```text

Priority:          P2

Case Age:          450 minutes

Remaining SLA:      30 minutes

```

### Result

```text

SLA Status:          AT_RISK

Escalation Required: True

Escalation Level:    Immediate SOC Lead Escalation

```

This demonstrates priority-aware SLA escalation.

A P2 case approaching its deadline receives stronger escalation than a P3 case with the same remaining time.

---

## Scenario 4 - SLA Breached

The baseline case is evaluated at:

```text

2026-08-14T12:26:12.686158+00:00

```

The SLA deadline was:

```text

2026-08-14T11:56:12.686158+00:00

```

Therefore:

```text

Case Age:          510 minutes

Remaining SLA:     -30 minutes

Priority:          P3

```

### Result

```text

SLA Status:          BREACHED

Escalation Required: True

Escalation Level:    Management Escalation

```

The negative remaining time confirms that the SLA deadline has been exceeded.

## SLA State Transition

The same case can move through multiple operational states over time.

```text

Case Created

   |

   v

WITHIN_SLA

   |

   | Deadline approaching

   v

AT_RISK

   |

   | Deadline exceeded

   v

BREACHED

```

The escalation behavior changes with the state:

```text

WITHIN_SLA

   |

   v

No Escalation

AT_RISK + P3/P4

   |

   v

SOC Lead Warning

AT_RISK + P1/P2

   |

   v

Immediate SOC Lead Escalation

BREACHED

   |

   v

Management Escalation

```

## Example Command

The engine can evaluate a case using a controlled timestamp:

```powershell

python ".\\scripts\\sla_monitor.py" `

--input ".\\evidence\\case-100111-within-sla.json" `

--output ".\\sample-output\\sla-within.json" `

--evaluation-time "2026-08-14T05:56:12.686158+00:00"

```

For normal operational use, `--evaluation-time` can be omitted and the current UTC time will be used.

## Limitations

This implementation is designed for a controlled SOC lab.

Current limitations include:

- Local JSON case input

- Static SLA thresholds

- No persistent case database

- No scheduled background monitoring

- No business-hours awareness

- No holiday calendar awareness

- No acknowledgement tracking

- No analyst workload context

- No automatic ticket updates

- No external notification delivery

- No case-management API integration
